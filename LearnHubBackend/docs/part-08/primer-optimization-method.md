# 前置教学：怎样做一次有证据的项目优化

## 1. 优化不是重写

优化的目标不是让代码看起来更复杂，而是让系统在同样的业务行为下更安全、更稳定、更容易维护，或者在明确的指标上更快。

一个合格的优化至少要能回答三句话：

1. 原实现在哪种场景下会出问题？
2. 新实现改变了什么机制？
3. 用什么证据证明改动没有破坏原功能？

例如，知识库详情缓存原来只使用 kbId：

    kb:detail:1

如果缓存中保存的是用户 A 的知识库 1，用户 B 请求知识库 1 时可能直接命中缓存。这里的问题不是速度，而是数据隔离。优化时优先修复正确性和安全性，再讨论性能。

## 2. 四种优化问题

### 2.1 正确性问题

程序结果和业务规则不一致，例如解绑时重复投递解析任务，或者 SUCCESS 任务仍保留旧错误。

### 2.2 安全性问题

用户可以通过缓存、接口参数或错误响应看到不属于自己的数据，或者公开仓库包含凭据。

### 2.3 性能和资源问题

慢 SQL、长事务、未关闭的 InputStream、无限增长的缓存，都会让系统运行一段时间后变慢。

### 2.4 可维护性问题

重复的 key 拼接、手工 JSON、无用依赖和错误的注解位置，会让下一次修改更容易出错。

## 3. 先建立基线

优化前先记录最小基线，不一定需要复杂压测：

- mvn compile 是否通过；
- mvn test 是否通过；
- health 是否返回 UP；
- 登录、知识库、文档、Chat 和出题主链路是否可用；
- 关键接口的 HTTP 状态码和响应结构；
- 数据库和 Redis 中是否出现异常状态。

基线的作用是防止“改完以后感觉应该没问题”。优化必须能比较前后。

## 4. Redis 缓存的四个问题

### 4.1 key 是否隔离

key 至少要包含决定数据权限的维度。知识库详情属于某个用户时，推荐：

    kb:detail:{userId}:{knowledgeBaseId}

公共配置才可以只使用对象 ID。

### 4.2 什么时候删除缓存

只要数据库中的数据被修改，就要考虑对应缓存：

- 更新知识库：删除详情缓存；
- 删除知识库：删除详情和关联文件列表缓存；
- 绑定或解绑文件：删除关联文件列表缓存。

常用模式是先写数据库，再删除缓存。它不是绝对强一致，但比只写数据库不删缓存可靠得多。

### 4.3 空值是否需要缓存

空列表如果不缓存，热点空知识库会每次都查数据库。Redis List 不能用“空 List”表示已经缓存过，所以可以使用一个不会和正常 ID 冲突的哨兵值：

    __EMPTY__

读取时识别哨兵并返回空列表，写入时同时设置 TTL。

### 4.4 TTL 不是失效策略的替代品

TTL 是最终兜底，不应该替代更新时的主动删除。修改后主动删除让下一次请求读到新数据；TTL 负责处理异常退出、遗漏路径和旧缓存。

## 5. 事务边界

事务应该覆盖必须原子完成的数据库写操作，而不是覆盖所有业务代码。

不推荐：

    开启事务
    调用 AI 网络接口
    等待模型返回
    写入数据库
    提交事务

模型慢、超时或重试时，数据库连接会被长期占用。

更合理的拆分是：

    非事务：权限校验、Qdrant 检索、AI 调用、JSON 校验
    短事务：插入 study_question 和 study_question_option

TransactionTemplate 适合这种场景，因为它可以在同一个 Service 中显式划出一个事务代码块，不依赖同类方法调用是否经过 Spring 代理。

## 6. 资源释放

从 MinIO、文件系统、HTTP 客户端取得的 InputStream 都应该明确关闭。推荐：

    try (InputStream inputStream = client.getObject(args)) {
        return parse(inputStream);
    }

try-with-resources 会在正常返回、异常和提前退出时调用 close。对网络流来说，close 不只是释放 Java 对象，还会归还 HTTP 连接。

## 7. 并发初始化

应用层的“先查再插”不是原子操作：

    A 查不到
    B 查不到
    A 插入
    B 插入

数据库唯一键和 INSERT ON DUPLICATE KEY UPDATE 可以把“只能有一条”的规则交给数据库保证。应用层仍然可以先做友好检查，但不能把它当作并发兜底。

## 8. 如何验证优化

验证分三层：

### 8.1 编译和已有测试

先运行：

    mvn -q -pl learnhub-application -am compile -DskipTests
    mvn -q -pl learnhub-application -am test

后续新功能不要求每次都新增测试，但已有测试不能被无意破坏。

### 8.2 手工接口回归

至少验证一个成功、一个权限失败、一个参数或资源失败。重点看 HTTP 状态码、错误码和数据库副作用。

### 8.3 状态和资源检查

查看 Redis key、任务表、额度流水、Qdrant 点数和日志，确认没有重复数据、旧错误或资源持续增长。

## 9. 优化的限制

本 Part 的改动仍然是单体应用级优化：

- Redis 不是强一致数据库；
- RabbitMQ 发送和数据库提交仍可能需要 Outbox 才能做到更强的一致性；
- AI 供应商延迟和可用性不由本项目控制；
- 没有压测数据时不能声称吞吐量提升了多少；
- 事务边界优化不能自动解决所有重复消费问题。

能清楚说出这些限制，比声称“已经高性能、高可用”更重要。
