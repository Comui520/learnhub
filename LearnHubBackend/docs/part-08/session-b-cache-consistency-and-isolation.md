# Session B：Redis 缓存一致性与数据隔离

## 1. 原来的两个风险

项目里缓存了两类数据：知识库详情，以及知识库绑定的文件 ID。它们的读取方式不同，风险也不同。

### 1.1 详情 key 没有用户维度

如果 key 是：

    kb:detail:1

读取流程可能是：

1. 用户 A 查询知识库 1，数据库通过归属校验；
2. A 的结果写入 Redis；
3. 用户 B 查询知识库 1，直接命中缓存；
4. B 没有再次经过数据库归属校验。

缓存命中速度越快，越容易把这个安全问题隐藏起来。

### 1.2 空列表不会真正进入 List 缓存

Redis List 对空列表没有元素。对一个没有绑定文件的知识库，写入空集合实际上什么也没有发生，下一次仍然会查数据库。

## 2. 详情缓存的修复

详情 key 改成：

    kb:detail:{userId}:{knowledgeBaseId}

读取时仍然建议先查数据库确认归属，再读取缓存，或者至少保证 key 已经包含所有权限维度。当前项目采用用户维度 key，避免不同用户共享同一条详情缓存。

更新和删除时必须使用完全相同的 key 规则：

    delete(kb:detail:userId:knowledgeBaseId)

只改读取 key、不改失效 key，会造成旧缓存继续存在。

## 3. 文件 ID 列表缓存

文件 ID 列表属于知识库，不直接属于用户，所以 key 可以使用：

    kb:df:kb:{knowledgeBaseId}

但它必须在以下操作后删除：

- 绑定文件；
- 解绑文件；
- 删除知识库；
- 任何改变关联表的批处理。

项目中新增了 60 秒 TTL。TTL 不是主动失效的替代品，而是遗漏失效路径时的最终兜底。

## 4. 空值缓存哨兵

项目使用：

    __EMPTY__

表示“数据库查询已经完成，结果确实为空”。读取时先判断哨兵，再返回 List.of()；不能把哨兵继续 Long.valueOf，否则会产生 NumberFormatException。

如果你以后把 List 缓存迁移为 JSON String，也可以直接缓存 []，但那会改变旧 Redis 数据的读取格式，需要考虑兼容或清理旧 key。

## 5. 缓存损坏怎么办

缓存不是唯一真相。当前实现遇到以下情况会回源数据库：

- JSON 反序列化失败；
- 文件 ID 不是合法数字；
- 哨兵格式不符合预期。

回源前删除坏值：

    redisTemplate.delete(cacheKey)

否则每次请求都会重复读取同一个坏缓存并重复失败。

## 6. 解绑为什么不再调用 bindDocuments

旧逻辑是：

    删除全部关联
    调用 bindDocuments 恢复保留文件

bindDocuments 除了插入关联，还会发送解析消息。因此每次解绑都会为已经解析的文件重复投递 RabbitMQ 消息。消费者虽然可以通过 SUCCESS 状态幂等跳过，但这仍然浪费队列和日志资源。

现在的逻辑是：

    删除全部关联
    直接插入保留的关联
    删除关联列表缓存

只有真正新绑定的文件才发送解析消息。

## 7. 修改顺序

推荐的数据库和缓存顺序是：

    1. 校验当前用户和资源归属
    2. 写数据库
    3. 删除相关缓存
    4. 返回结果

不要在数据库写入失败时先删除缓存，也不要只更新缓存不更新数据库。

## 8. 仍然存在的限制

当前方案不是分布式强一致缓存：

- 数据库提交成功、Redis 删除失败时，旧值可能继续存在直到 TTL；
- 多个实例之间没有缓存失效广播；
- 缓存删除和事务提交不是同一个原子操作；
- 如果未来需要更强一致性，可以学习事务消息、Outbox 或 CDC。

对当前学习项目来说，用户维度 key、主动删除和 TTL 已经是合理的基础方案。
