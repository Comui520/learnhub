# Session E：交付清单与继续学习

## 1. 什么时候算完成

完成 Part 8 不是表示项目已经达到生产级高可用，而是表示你拥有一个可以继续学习和展示的稳定基础。

至少满足：

- main 分支能编译；
- 应用能在本机 Docker 基础设施上启动；
- 登录、知识库、文档、解析、RAG、AI 出题、答题和额度链路可演示；
- README 能让别人知道如何配置和启动；
- 公开仓库没有真实凭据；
- 关键优化能说出原因、边界和验证方法。

## 2. 新功能为什么不要求立即补很多测试

测试是回归工具，不是功能数量的计数器。以后新增功能时，可以先用接口验收和日志确认主链路，避免每个小改动都扩展大量测试维护成本。

但以下场景仍值得保留测试：

- 修改登录、权限和额度等高风险逻辑；
- 修复曾经出现过的回归 Bug；
- 重构公共组件或事务边界；
- 准备发布前的关键验收。

当前项目保留已有测试作为安全网，不把“所有新功能都有完整测试”作为学习推进的硬门槛。

## 3. README 应该写什么

根 README 面向第一次打开仓库的人，回答：

1. 这个项目是什么？
2. 它用到了哪些核心技术？
3. 目录如何组织？
4. 如何在本机启动？
5. 密钥放在哪里？
6. 它明确不是什么？

LearnHub 的定位是学习基础，不要把它宣传成已经验证盈利的生产级 Agent 平台。可以诚实说明：它用于学习 Spring Boot、Spring AI、RAG 和常见基础设施，并作为后续实验的起点。

## 4. Git 提交策略

主仓库现在是 D:\LearnHub 汇总仓库，backend 作为普通目录存在。

每次优化前先创建 tag 或 commit：

    git tag -a part8-pre-optimization-20260914 -m "checkpoint"

优化完成后再创建一个描述清楚的提交。提交信息应说明意图，例如：

    fix: isolate knowledge-base cache by user
    perf: move AI call outside database transaction
    test: repair Redis-backed login attempt tests

避免使用“update”“修改一下”这种无法帮助排查历史的提交说明。

## 5. backend 历史的处理

原 backend 历史保存在本机备份目录，公开主仓库使用新的 monorepo 历史。这样可以保证：

- GitHub 上能看到当前汇总仓库的清晰提交；
- backend 源码不是嵌套仓库指针；
- 未经审计的旧历史不会意外携带敏感内容；
- 旧历史仍可在本机用于追溯。

如果以后需要把旧历史正式迁移到主分支，应先使用历史重写工具给路径加 LearnHubBackend 前缀，再完成全量密钥扫描和强制推送。这不是当前学习项目的必要步骤。

## 6. 后续专题选择

Part 8 以后不需要继续堆功能。可以按兴趣选择一个专题深入：

- Spring Security：方法级权限、Refresh Token、主动注销；
- Spring AI：Tool Calling、结构化输出、Agent 循环；
- RAG：重排、混合检索、评测集和引用质量；
- 异步系统：Outbox、幂等、重试、死信和任务状态机；
- 数据库：慢 SQL、索引、锁和隔离级别；
- 前端：SSE 消费、登录态、文件上传和错误展示；
- 部署：镜像、反向代理、HTTPS、监控和备份。

每次只选择一个问题，先建立实验，再比较方案。

## 7. 面试表达模板

介绍项目时可以按照下面顺序：

    我做了什么业务
    为什么选择 Spring Boot 和模块化单体
    RAG 的检索、过滤和引用如何保证
    RabbitMQ 解决了什么耗时问题
    Redis 用于什么，以及缓存失效如何处理
    额度扣减和支付回调如何保证幂等
    项目目前的限制和下一步是什么

不要只报技术名词。面试官更关心你是否理解边界、故障和取舍。
