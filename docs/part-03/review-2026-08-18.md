## P0：必改

### 1. downloadContent 用错了 MinIO 对象名

> ✅ 2026-08-18 已随重构修复：`downloadContent` 改用 `file.getObjectName()`，且先经 `getOwnedFile` 校验归属。

`DocumentServiceImpl.downloadContent` 里：

```java
.object(document.getFileName())
```

应该是 `.object(document.getObjectName())`。

原因：MinIO 里对象名是 `documents/{userId}/{sha256}/{文件名}`，`getFileName()` 只是原始文件名，MinIO 里根本没有这个对象 → 流式下载必然 NoSuchKey / 500。presigned share-url 用的是 `getObjectName()`，所以之前测着没问题；你改成流式方案后这个 bug 就会暴露。

### 2. 删除文档会误删被其他记录引用的 MinIO 对象

> ✅ 2026-08-18 已随重构修复：拆表后删除“库里的文档”= 删关联记录，`countByFileId == 0` 才删文件记录 + MinIO 对象。

`deleteByUserIdAndId` 现在无条件 `removeObject`。同一用户把同一文件传到两个知识库（`uk_kb_sha256` 允许跨库重复）时，两条 document 记录指向同一个 objectName。删其中一条会把对象删掉，另一条变死链。

修法（Part 3 Session C 已经写过）：删除记录后再查 `existsByObjectName(objectName)`，没有其他引用才删 MinIO；MinIO 删除失败要 catch + `log.error`，不能往外抛（尽力而为）。

### 3. 删除知识库没检查“还有文档”

> ✅ 2026-08-18 已随重构修复：`KnowledgeBaseServiceImpl.delete` 先 `countByKnowledgeBaseId(id)`，> 0 抛 `KNOWLEDGE_BASE_HAS_DOCUMENTS`（409）。

Session B 的设计是“有文档就 409 拒绝删除”，你现在直接 `removeById`，会留下孤儿 document 记录。

修法：删之前 `count` document where knowledge_base_id = id，> 0 抛一个 409 业务错误（比如 `KNOWLEDGE_BASE_HAS_DOCUMENTS`）。

> ✅ 2026-08-18 已随重构修复：`DocumentService` / `KnowledgeBaseService` 接口不再继承 `IService`，Controller 只调用业务方法，IService 能力留在 ServiceImpl 内部。
