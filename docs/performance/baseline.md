### 模型切换与 Chat 阶梯压测

| 模型 / 场景 | 并发 | 结果 | 说明 |
|---|---:|---|---|
| `Qwen/Qwen3.5-4B` Chat | 1 次 | 超时 | 单次请求超过 60 秒，未继续加压 |
| `deepseek-ai/DeepSeek-V4-Flash` Chat | 1 次 | 成功 | HTTP 200、SSE 正常，p95 11.67 秒 |
| `deepseek-ai/DeepSeek-V4-Flash` Chat | 3 VU / 20 秒 | 10 次成功、约 5,011 次被限流 | 同一用户触发后端 `5 次 / 10 秒` 的用户级限流；成功请求没有出现 SSE 认证错误 |

这轮阶梯测试的主要结论不是“模型可以承受 3 VU”，而是验证了限流保护：同一个用户超过 5 次 / 10 秒后，后续请求被快速拒绝，避免无限消耗模型和额度。要测模型真实并发吞吐，需要准备多个测试用户，或在专用压测 profile 中调整限流参数。

### 多用户真实 Chat 压测

为绕开单用户限流，创建了 8 个临时测试用户，每个用户充值 20 credits，并为每个用户创建独立知识库、上传并完成解析一份小 Markdown 文档。随后使用 8 个 VU，每个 VU 对应一个用户和一个知识库，持续 60 秒压测 DeepSeek Chat：

| 指标 | 结果 |
|---|---:|
| 测试用户 / VU | 8 |
| 持续时间 | 60 秒 |
| Chat 成功请求 | 98 |
| 被限流 / 失败请求 | 5,664 |
| Chat 成功 p95 | 12.54 秒 |
| Chat 成功 p99 | 约 56.62 秒 |
| 成功请求错误率 | 0% |
| 测试账号总额度 | 160 → 62 credits |

总额度从 160 降到 62，正好对应 98 次成功 Chat 扣减；失败的 5,664 次主要是每个用户的 `5 次 / 10 秒` 限流响应，没有继续消耗额度。这个结果证明了多用户场景下 SSE 链路可以同时处理真实请求，但当前瓶颈仍然是模型响应时间和每用户限流策略，而不是 Nginx 或基础 CRUD 接口。

### 外部 AI / 写入专项（单次或极小次数）

| 场景 | 次数 | 结果 | 延迟 / 结果 |
|---|---:|---|---:|
| Chat SSE（首次尝试） | 1 | 失败，发现 SSE 异步安全上下文问题 | 后端出现 `AuthorizationDeniedException`，已修复 |
| Chat SSE（修复后） | 1 | 成功，HTTP 200，SSE 内容完整 | p95 4.43 s，错误率 0% |
| AI 生成单选题 | 1 道 | 成功并落库，题目 ID 为 6 | p95 5.94 s，错误率 0% |
| 文档上传冒烟 | 1 个小 Markdown | 成功，测试文档随后删除 | p95 79.87 ms，错误率 0% |
| 支付幂等回调 | 同一订单 5 次 | 全部 HTTP 200，数据库仅 1 条 `GRANT` 流水 | p95 63.64 ms，错误率 0% |

Chat 专项第一次失败消耗了 1 credit；修复后的成功请求又消耗了 1 credit。测试完成后账户余额为 119.01，说明本轮只发生了两次 Chat 扣减和一次 0.01 的模拟订单入账。


## 结论

在本次 Windows + Docker Desktop、5 VU、10 秒、本地演示数据的基线中，三个非 AI 场景均为 0% HTTP 错误率，p95 分别为 4.32 ms、5.41 ms 和 9.66 ms。结果说明当前演示数据规模下，基础 Web、额度读取和题库分页链路运行正常；它不代表公网生产容量，也不能外推 AI Chat 的吞吐量。
